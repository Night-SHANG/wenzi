# v0.8 party builder check

Recorded: 2026-11-07, Beijing time (UTC+08:00). Scope: read-only design/source inspection; this report is the only edit. No implementation, test execution, or subagents.

## Decision

**No blocking architecture contradiction found. Proceed with the three workers and root integration.** The design has sufficient contracts for a competent implementer to build a real, repeatable party loop. Root retains final design rulings. The clarifications below are small integration decisions, not a reason to reopen the design or request user confirmation.

- **Single authorities:** leader HP remains in the original vitals provider; companion HP belongs to party; enemy HP/queue/phase belong to party-battle. The selection adapter saves only the selected member. Inventory, experience, skills cooldowns, effects and quests retain their existing owners. Separate squads and tactics avoid importing grid-specific HP/position ownership into the adventure.
- **Legacy shapes/saves:** new combat-action and encounter-records protocols avoid changing encounters.enemyHp semantics. The explicit duel/skills/quests/view migrations preserve existing state; old worlds without a session binding retain the old duel route. Adding a blank session to an already engaged legacy world deliberately fails rather than inventing an owner.
- **Playable loop:** a living companion can continue after the leader falls; every party action advances its cursor before bounded enemy processing; the next round includes all frozen participants, allowing the specified revival behavior. Victory/defeat remain terminal while recovery is possible; claim/retreat release the lease and start cooldown; persistent damage plus real recovery allows subsequent encounters.
- **Worker split:** the three file sets are disjoint. Root owns the two consumers, text composition, world assembly, registry and actual integration. Independent fixtures can exercise the public protocols without accessing provider state. No fourth implementation worker or host change is necessary.

## Decisive integration clarifications

1. **Pin the location of `skills.list.targets` before root implements the view.** The spec says the new path adds a targets array but does not say whether it is top-level or attached to each skill. Recommended ruling: return `{ skills: [...], targets: [...] }` on the generic path, with target entries exactly the validated combat-action targets; preserve the old `{skills:[...]}` shape on the legacy path. `loadout-view` reads the optional top-level list once and creates per-target `use({skill,target})` hints. This is entirely root-owned and need not delay any worker.

2. **Rule on mixed-world consumer routing: explicit bindings cannot disable the generic path.** `src/engine/index.ts:213–228` automatically binds an optional capability when exactly one compatible provider exists; bindings accept only valid provider IDs, with no opt-out. Therefore in a world containing duel and party controllers, every upgraded skills instance selects party combat-action even while duel owns the session, and every upgraded quest log selects party encounter-records even if its encounters binding explicitly points to duel. Creating separate skills/log instances does not fix this. The example party world removes duel, and unchanged legacy worlds have no generic provider, so their loops remain valid. **Decisive choices:** (a) document that mixed controllers can coexist but built-in skills/quests are party-routed whenever the generic provider exists; or (b) add backward-compatible optional source-selection configuration to root-owned skills and quests, defaulting to the current specified priority. The latter enables one explicitly selected source per consumer without changing the host. Do not silently phase-switch skills, infer intent from encounter IDs, or claim separate instances alone permit selecting duel. This is a conditional blocker only if full legacy skills/quests in a mixed world are part of the advertised compatibility promise; root must settle that promise before publishing it.

## Concrete implementation traps to preserve

- **Transaction timing is compatible with the lock design.** `src/engine/index.ts` runs module validation after the outer command and event dispatch, rather than after every nested call. Therefore acquire-before-battle-write and release-before/after-clear can be safe within one command. Do not add eager cross-module validation inside session.acquire/release that demands the other module has already updated its battle; that would create a circular handshake. Controllers validate their own lease at stable boundaries and check session command results against status.
- **Do not normalize turns in queries or provider validators.** Only start/attack/strike advance the combat queue. The controller's command must write the completed phase/cursor before returning; status/restore validation checks the invariant. An externally issued HP mutation that would leave an active current actor dead must fail final validation and roll back, unless an authorized controller transaction also advances the queue. Recovery of another unit does not grant an extra turn.
- **Use the leader ID, not the current ally ID, for generic skills.** `actionStatus.canAct` is false on companion turns even though ordinary party attack is available. Validate optional/explicit target and canAct before inventory/effects; after performStrike validate the returned generic status and the actual queried status. AI failure late in the same command must roll back paid costs, effects, HP, queue and skill cooldown together.
- **Freeze facts, independently validate current content.** A deleted recruited companion stays usable from its frozen roster record; a deleted current encounter stays resolvable from Battle for claim/retreat. Neither case permits skipping validation of the remaining current catalog. For terminal defeat, later healing must not force the controller back to active or make the terminal save invalid.
- **Keep the shared-session premise explicit.** The protocol coordinates explicitly bound controllers; it is not authentication and cannot discover every controller sharing a health provider. Two controllers bound to different session instances are an authoring misconfiguration, not proof that the exclusive protocol failed. An arbitrary orphan acquisition is likewise a trusted local authoring operation; document recovery/binding limits rather than silently clearing ownership.
- **Parallel tests must not assume another worker's runtime exports already exist.** Fixtures decouple capability behavior, not JavaScript imports. Workers can write their own consumer-side validation against the fixed wire shapes and use type-only imports, or add producer-reader imports after those files exist. Do not introduce temporary duplicate public protocols or edit another worker's files to unblock a test.
